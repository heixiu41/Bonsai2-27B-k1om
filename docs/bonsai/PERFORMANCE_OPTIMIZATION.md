# k1om 推理性能：分析与优化方向（已修正）

> **本文档替代了早期版本。** 早期版本基于一次错误的带宽测量（244 线程 3.32 GB/s），
> 并据此得出"带宽会挡住优化"的结论。**那个结论是错的。**
> 下面所有数字都是重做基准后的实测值。

---

## 当前实测基线

```
配置                                    decode
标量 + OpenMP（无向量化解包）            0.161 tok/s
IMCI 内核修复 + 向量化解包（默认）        0.267 tok/s
  ├─  61 线程                           0.273
  ├─ 122 线程                           0.289   ← 目前最优
  └─ 244 线程                           0.269

正确性：全部 MATCH（top-1 = 11751 ' Paris'，rank 0/248320）
```

## 关键结论：**计算绑定，不是带宽绑定**

```
每 token 必须流的 PQ2_0 字节 = 7,137,280,000 (7.137 GB)
每 token 权重总数            = 26,869,760,000

实测带宽（6.87 GB buffer，3 次取最好，244 线程）:
    contiguous    62.45 GB/s
    rows-1360    196.43 GB/s   ← 推理内核正是这个访问模式
    rows-340     103.54 GB/s
    interleaved   47.37 GB/s
    峰值（官方）  352 GB/s

→ 访存耗时 = 7.137 GB ÷ 196.43 GB/s = 36 毫秒
→ 实际每 token 耗时                = 3456 毫秒
→ 访存占 1%，计算占 99%
```

**带宽有 95 倍余量。** 理论上限约 `196 GB/s ÷ 7.137 GB = 27.5 tok/s`（单就访存而言）。
**所以不要再去优化访存模式** —— 那不是瓶颈。

### 之前那个错误数字的教训

早期基准只读 **1 GB**，而卡有 15.5 GB 内存 —— **大概率整块命中缓存**；
再加上 0.010 秒的读数撞上了计时器分辨率。得到：
```
seq 1 thread  1.57 GB/s
seq half      6.51 GB/s
seq all       3.32 GB/s   ← 被误用为"实测带宽"
rows half   104.32 GB/s   ← 当时判定"是计时假象"丢掉了 —— 那才是真数据
```
**两个教训**：(1) 基准的工作集必须远大于缓存；(2) 不要因为数字"超出预期"就丢弃测量结果。

## 计算为什么慢

子代理实测的单线程吞吐：
```
解码 10240×5120 (DRAM 流式)   589.7 M 权重/s
解码 1024×32   (L2 驻留)     1254.4 M 权重/s   ← 纯计算可到 2.1x
matvec 10240×5120            0.4993 s → 0.1008 s（4.98x）

纯解码耗时 = 26,869,760,000 ÷ 589.7e6 = 4.11 秒
实际每 token 耗时                     = 3.75 秒
→ 解码占约 110% 的时间 ⇒ 计算完全主导，内存延迟已被掩盖
```

**根因**：解码器每 128 个权重需要 **16 次 `vpermd`**（4 次 load + 8 次广播 permute
+ 8 次 LUT permute + 8 次 srlv + 8 次 mul + 8 次 store）。
而 **KNC 上 `vpermd` 和 `vloadunpackld` 都是微码指令（microcoded）**，吞吐远低于普通向量指令。

## 优化方向（按杠杆大小）

### ① 降低 `vpermd` 密度 —— 唯一的数量级杠杆

**未做的实验（优先）**：早先试过用 IEEE-754 位运算做 int→float 转换
（`(float)c == bitcast_ps(c + 0x4B000000) - 8388608.0f`），对 `|c| ≤ 2` 应当精确，
但实测**负值出错**（`-1` 变成 `-0`，`+1`/`+2` 正确），
而我**当时没查清原因就放弃了**。

按 IEEE-754，`0x4B000000 + (-1) = 0x4AFFFFFF` 应表示 8388607.0，
减 8388608.0 得 -1.0。所以要么是 `_mm512_castsi512_ps` 在 KNC 上的行为，
要么是编译器常量折叠，要么是上游某处已经错了。

**若这条路走通，每 16 个浮点可省掉 2 次 `vpermd`**，预期 1.3–1.5x。
排查建议：直接打印 `_mm512_add_epi32(c, bias_i)` 的原始位模式，逐步定位。

> 子代理的另一项实测：bias trick **确实精确**（`k = code&3` 永不为负），
> 但比 LUT 慢 **2.2 倍**（290 vs 1255 M 权重/s），因为
> `vpermd` 换成了 `vpandd + vpaddd + vsubps`，而 **KNC 的 512 位整数 ALU 是慢路径**。
> 所以"省 permute"的思路需要重新设计，不能直接换成整数运算。

### ② 软件预取（便宜）

KNC 有 `_mm_prefetch`。在 block 循环里提前取下一 block。
**注意**：`lo/hi` 对会读 `[blk, blk+81]`（3 个对齐块），预取要覆盖这个跨度。

### ③ 线程数默认改 122（已实测，免费 7%）

```
 61 线程  0.273 tok/s
122 线程  0.289 tok/s   ← 最优
244 线程  0.269 tok/s
```

### ④ 减少 OpenMP 区域创建

每层几十个 matvec，每个都新建/销毁线程组。64 层 × 几十次 = 数千次。
改成外层一个 `#pragma omp parallel`、内部只用 `for`。
预期收益小（同步开销在秒级总时间中占比低），但便宜。

### ⑤ 不推荐：定点累加

曾被考虑用来避开浮点转换。**两个理由否定它**：
1. KNC **没有** `_mm512_madd_epi16` / `maddubs_epi16` / `mullo_epi16`
   （链接器证明，见 `KNC_INTEGER_SIMD.md`）—— 整数乘加路线不存在
2. 真定点累加需要先把 `x` 量化成整数，**其误差远大于浮点求和顺序噪声**

## 数值上的天花板

```
196.43 GB/s（rows-1360 实测）  →  27.5 tok/s   ← 若解码变成零成本
352.00 GB/s（硬件峰值）        →  49.3 tok/s
```
**所以即使解码优化到极致，也只是逼近 27 tok/s。** 而当前 0.289 tok/s
距此还有 **95 倍** —— 全部在计算上。

## 一句话总结

**0.289 tok/s 是纯粹的计算瓶颈。** 唯一的大杠杆是降低解码的 `vpermd` 密度；
带宽（196 GB/s）在 27 tok/s 以内都不会成为限制。
